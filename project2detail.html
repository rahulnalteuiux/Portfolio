The Problem Space

Engineering teams managing enterprise software assets relied on disconnected, folder-based version tracking systems. Changes were frequently overwritten, audit trails were incomplete, and there was no structured way to manage responsibilities across different roles.

The objective was to design a unified enterprise version control platform with clear role-based workflows, complete traceability, and a modern information architecture that could scale with growing engineering teams.

Users Goals
  • Replace legacy folder-based version tracking
  • Enforce role-based access control
  • Ensure complete audit trail and traceability
  • Reduce version conflicts and overwrites
  • Support multi-team collaboration at scale

UX Strategy

Designing for Clarity & Traceability

The redesign focused on reducing the effort required to find, understand, manage, and verify project information. The experience was reorganized around the engineer's workflow: discover → manage → update → review → verify.

→
01
Make Information Discoverable
Surface project, version, status, documentation, and activity information clearly so engineers can find what they need faster.
02
Build Traceability into the Experience
Connect changes with the responsible user, timestamp, version, and related project activity to make history easier to understand.
03
Structure Complex Information
Use clear hierarchy, categorization, filtering, and predictable navigation to make large technical datasets easier to explore.
04
Support Role-Based Workflows
Present relevant information and available actions according to the user's responsibilities, permissions, and workflow needs.
05
Provide Context Before Action
Give engineers enough context about the project, version, status, and history before they make important changes or approvals.

Design Decisions

Five decisions that shaped the experience.

01
Dashboard

Turned the dashboard into an orientation layer.

Prioritized recent updates, versions, activity, and actions so engineers could understand what mattered first.

02
Repository

Made version management easier to scan and act on.

Structured information around Identify → Compare → Verify → Act instead of exposing technical data without hierarchy.

03
Version Detail

Brought related context into one workspace.

Connected project details, technical metadata, documents, certification, and activity to reduce cross-screen searching.

04
Upload Workflow

Separated entry, validation, review, and submission.

Created clear stages that help users verify information before committing high-impact changes.

05
Governance

Made traceability visible throughout the system.

Connected activity through Who · What · Where · When · Context to make project history easier to verify.

Key Challenges

Simplifying complexity
without losing context.

01
The Design Tension

The system contained detailed technical information required for version management, troubleshooting, review, and accountability. The challenge was making that information easier to navigate without hiding what expert users needed.

Too much information

High cognitive load

Showing every technical detail at the same level made routine tasks harder to scan and increased the effort required to find important information.

Dense data Long scanning Hidden priorities
↔
Too little information

Loss of context

Removing technical details completely would make it harder for engineers and reviewers to investigate changes, understand history, and verify project information.

Missing context Limited verification Reduced confidence
Design Response

Progressive disclosure

Surface the information needed for the immediate task first, while keeping deeper technical context available when users need to investigate, compare, verify, or review.

01
Operational layer

Project status · Current version · Recent activity · Primary actions

02
Detailed layer

Version metadata · Documentation · Approval history · User activity

03
Verification layer

Change context · Audit trail · Ownership · Supporting records

Problem Solving

From Complexity to Clarity

Each design decision addressed a specific point of friction in the version-management workflow—making information easier to find, understand, verify, and act on.

→
01
Information Architecture

Finding the right version should not require investigation.

Before

Scattered information

Engineers had to search across different areas to determine which version was current and what information supported its status.

→
Design Move

Context-first repository

Project, version, status, ownership, and supporting metadata were brought into a single, scannable structure.

→
Result

Faster verification

Users could identify and verify version information without reconstructing the context themselves.

02
Traceability

Change history should tell a story, not require reconstruction.

Before

Disconnected records

Understanding what changed, who changed it, and when it happened required users to connect information manually.

→
Design Move

Connected activity history

Activity and version history were tied directly to the relevant project and version context.

→
Result

Understandable audit trail

Users could follow the evolution of a version without manually reconstructing the project's history.

03
Submission Workflow

High-impact changes need a deliberate verification point.

Before

Too much at once

Version updates involved metadata, documentation, certification, review, and submission across one complex flow.

→
Design Move

Structured submission stages

The workflow was divided into explicit stages: identify → define → upload → document → certify → review → submit.

→
Result

Controlled commitment

Users received a clearer verification point before committing high-impact version changes.

Technical Constraints

Simplifying the experience
without hiding the system.

→
01
System Constraint

Data relationships

Projects, versions, documents, certifications, approvals, and activity needed to remain connected.

Design Response

Simplified the user's mental model while preserving the relationships between connected records.

02
System Constraint

Permissions

Different users have different responsibilities and access requirements.

Design Response

Structured actions and information around role-aware behavior and access.

03
System Constraint

Implementation feasibility

Some apparently simple interactions could introduce disproportionate backend complexity.

Design Response

Absorbed complexity through clear grouping, sensible defaults, validation, and contextual guidance.

04
Portfolio Constraint

NDA protection

Product names, screenshots, infrastructure details, datasets, and organizational identifiers are protected.

Design Response

Used anonymized and reconstructed representations while preserving the UX problem-solving narrative.

Design principle Reduce cognitive complexity — not system complexity.

"Enterprise UX is about information confidence: engineers need to understand what is current, approved, changed, and supported before they can confidently make decisions."

Enterprise tables can become decision-making tools: when structured around discovery, comparison, verification, and action, dense datasets can support everyday engineering workflows.
